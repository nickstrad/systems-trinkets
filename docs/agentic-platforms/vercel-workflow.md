# Vercel Workflow: event log, queue, and stateless execution

Research snapshot: 2026-09-29. Workflow Development Kit (WDK), now called Workflow SDK/Vercel Workflows in newer Vercel writing, supplies durable execution for long-running TypeScript workflows. This note extracts mechanisms for future lessons; the SDK itself is not configured in this repo. [WDK launch, 2025](https://vercel.com/blog/introducing-workflow); [GA architecture post, 2026](https://vercel.com/blog/a-new-programming-model-for-durable-execution).

## Execution path

`"use workflow"` marks the orchestration function; `"use step"` marks retryable units that may perform external work. WDK's build integration generates handlers for workflows and steps and registers them as HTTP routes. Vercel's managed World uses three components: an append-only **event log** for run history, **Vercel Queues** for wakeups and handoff, and application functions on **Fluid compute** for execution. The library in a function dequeues, loads state, executes, and enqueues follow-on work; a step is a separate function invocation. There is no continuously running application workflow process while it sleeps or awaits a hook. This is an architectural statement about the managed World, not proof that Vercel has no internal queue or control-plane service. [WDK framework integration](https://vercel.com/blog/inside-workflow-devkit-how-framework-integrations-work); [GA architecture post](https://vercel.com/blog/a-new-programming-model-for-durable-execution); [WDK launch](https://vercel.com/blog/introducing-workflow).

```text
start/run request -> workflow route -> event log -> queue -> function invocation
                                             ^                       |
                                             | step result + next wakeup
                                             +-----------------------+
```

The SDK's **World** interface swaps execution, queue, and persistence implementations. Vercel documents a Local World, managed Vercel World, and a self-hosted PostgreSQL reference World. The public repository's world manifest describes the PostgreSQL World as PostgreSQL durable storage plus Graphile Worker jobs. The local World does not by itself establish crash durability across machines; use the PostgreSQL implementation for a persistent reference. The SDK is research context; local lessons implement the mechanisms in Go rather than adding a second application language. [WDK launch](https://vercel.com/blog/introducing-workflow); [World manifest](https://github.com/vercel/workflow/blob/main/worlds-manifest.json).

## Replay, failure, and scale

Step inputs and outputs are recorded. On a wakeup or failure, workflow code can replay its control flow from the event history while completed step results are reused; side effects belong inside steps. As of Workflow 4.1 beta (2026-02-03), run, step, and hook state is materialized from an append-only event log rather than mutable entity records. Vercel says route replay can detect missing queue messages and re-enqueue them. This is recovery of **workflow state**; a step that succeeds externally but crashes before its success is recorded may run again. Thus externally visible effects still need idempotency keys or a transactional design. The latter is an inference from the recorded-result boundary, not a claim of a documented Vercel failure trace. [WDK launch](https://vercel.com/blog/introducing-workflow); [event sourcing changelog](https://vercel.com/changelog/workflow-event-sourcing).

`sleep`, hooks, and webhooks persist a wait and release compute until a timer or external event resumes the run. Parallel independent steps can run concurrently; each retry boundary is per step. Durable streams allow reconnecting clients to resume output. The managed World scales by invoking functions for runnable steps and sending handoffs through Queues, whereas a suspended run consumes log storage without an active function. Vercel's 2026 GA post reports over 100 million runs and 500 million steps since beta, and its February changelog claims many thousands of steps per second for the queue path; these are vendor adoption/throughput claims, not a disclosed benchmark, capacity limit, or per-tenant fairness guarantee. [GA architecture post](https://vercel.com/blog/a-new-programming-model-for-durable-execution); [event sourcing changelog](https://vercel.com/changelog/workflow-event-sourcing); [parallel-step teaching example](https://vercel.com/academy/svelte-on-vercel/multi-step-workflows).

## Bounded lesson candidates using configured software

1. **Event history versus mutable status.** With Go, PostgreSQL, and DuckDB (`Configured: yes`), execute a three-step job. Baseline: overwrite a `status` row; comparison: append input, step-start, step-result, and wakeup events and reconstruct the run. Invariant: after a crash/restart at every boundary, completed step outputs remain stable and reconstructed state equals an uninterrupted reference run. Kill the worker after an external-effect write but before result append to demonstrate why an idempotency key and unique constraint are necessary. Measure replay time versus history length, duplicate attempts versus effects, write amplification, and recovery lag. [Event sourcing changelog](https://vercel.com/changelog/workflow-event-sourcing); [WDK recorded results](https://vercel.com/blog/introducing-workflow).
2. **Sleeping without holding a worker.** With PostgreSQL and NATS JetStream or Valkey Streams (`Configured: yes`), compare a worker blocked on an in-process timer with a persisted due time plus queued wakeup. Stop all workers across the deadline, restart, and reconcile overdue timers. Invariant: each scheduled action eventually completes and its business effect occurs once, including duplicate wakeups. Measure resident workers during wait, wakeup lateness, queue redeliveries, and reconcile time under bounded concurrent jobs. This models the distinction between durable timers and process timers; it does not exercise Vercel's queue. [WDK launch](https://vercel.com/blog/introducing-workflow); [Vercel Queues docs](https://vercel.com/docs/queues).
3. **Retry granularity and fan-out.** With Temporal (configured Go SDK/dev server) or a small PostgreSQL-backed runner, compare one large step that processes N independent items with N steps joined after completion. Make one item fail transiently. Invariant: all N results appear once; no successful item needs its external effect repeated. Measure repeated work, p95 completion time, event count, and queued/running concurrency. Keep the same failure schedule and input for both variants. [Vercel parallel-step example](https://vercel.com/academy/svelte-on-vercel/multi-step-workflows).

## Future gaps and open questions

The Workflow SDK and Graphile Worker are not `Configured: yes`; a direct WDK/World lesson would require a catalog/setup decision. Managed Vercel Queues and Fluid compute are vendor services, not local substitutes. Vercel has not published all managed storage internals, queue scheduling/fairness, or a reproducible scale benchmark. Its April 2026 post lists a snapshot-based replay runtime and native concurrency controls as **future work**, so do not describe them as current guarantees. The public PostgreSQL World is useful source code to inspect, but its behavior should be verified at a pinned version before making a lesson depend on it. [GA architecture post](https://vercel.com/blog/a-new-programming-model-for-durable-execution); [World manifest](https://github.com/vercel/workflow/blob/main/worlds-manifest.json).
