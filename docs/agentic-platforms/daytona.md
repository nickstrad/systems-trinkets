# Daytona: sandbox control plane and lifecycle

Research checked 2026-09-29. This is a design study, not a tested Daytona deployment. The links point to Daytona's own documentation as read on that date; hosted behavior and limits may change.

## What the platform does

Daytona exposes SDK, CLI, dashboard, MCP, and SSH interfaces. Its NestJS REST API authenticates requests and owns lifecycle, allocation, snapshots, and volumes. A sandbox manager in that API schedules work and reconciles desired and actual state. Runners poll the API for jobs and perform create/start/stop/destroy/resize/backup operations. A daemon inside each sandbox implements the Toolbox API for process execution, files, Git, terminals, logs, and computer use. Preview traffic takes a separate host-routed HTTP/WebSocket proxy path: `{port}-{sandboxId}.{proxy-domain}` resolves a runner and forwards to it. PostgreSQL stores metadata; Redis handles cache, sessions, and distributed locks. [Architecture](https://www.daytona.io/docs/en/architecture/)

The default sandbox is a **Linux container**. Daytona also has Linux VM, Windows VM, GPU, and macOS classes. Its runner documentation describes Linux namespaces for process, network, mount, and IPC isolation. A container's isolation must not be described as a dedicated guest kernel: the VM class is a distinct runtime and feature set. Daytona markets sub-90 ms creation on its site; that is a vendor claim with unspecified workload, region, quantile, and measurement boundary, not a local result. [Sandboxes](https://www.daytona.io/docs/sandboxes) · [Architecture](https://www.daytona.io/docs/en/architecture/) · [Vendor speed claim](https://www.daytona.io/)

## State and scale mechanics

The snapshot builder pulls or builds container images and pushes them to an internal OCI-compatible registry backed by S3-compatible storage; runners pull from it. Container snapshots from an existing sandbox capture filesystem state only. Linux/Windows VM hot snapshots can include memory, and VM forks branch filesystem and memory. These are separate mechanisms from an OCI image layer. [Architecture](https://www.daytona.io/docs/en/architecture/) · [Snapshots](https://www.daytona.io/docs/snapshots/)

Stopping a container preserves its filesystem on its runner and clears RAM; archiving moves that filesystem to object storage. VM stop offloads filesystem state to nearby storage, while VM pause preserves memory too. Auto-stop defaults to 15 minutes for container sandboxes and auto-pause to 60 minutes for VMs in the documentation checked. A wall-clock TTL can destroy a sandbox regardless of activity. [Persistence](https://www.daytona.io/docs/en/persistence/) · [Sandboxes](https://www.daytona.io/docs/en/sandboxes/)

S3-backed FUSE volumes survive sandbox deletion and may be mounted by multiple sandboxes. Daytona says writes are immediately visible but concurrent writes to one path are last-writer-wins, not transactional. `subpath` limits each mount's visible tree. This is a useful contrast with a sandbox's private filesystem. [Volumes](https://www.daytona.io/docs/en/volumes/)

For fast fan-out, a warm pool keeps already-running sandboxes from one snapshot in one region. A claim requires an exact match on snapshot, region, default resources, default user, and absence of custom environment variables, volumes, or secrets. Claims trigger background replenishment; pool capacity consumes organization quota. This is an admission and inventory problem as much as a startup optimization. Warm pools require organization enablement, so availability is not universal. [Warm pools](https://www.daytona.io/docs/en/warm-pools/) · [Troubleshooting](https://www.daytona.io/docs/en/troubleshooting/)

The published architecture identifies horizontally scaled runners, but does not establish a universal per-runner density, placement algorithm, or end-to-end startup latency distribution. A lesson should measure its own host and avoid importing the vendor's headline number. [Architecture](https://www.daytona.io/docs/en/architecture/)

## Bounded lesson candidates using configured software

1. **Warm-pool claim versus cold provisioning, modeled at the control plane.** Build a Go request handler with PostgreSQL (`postgres://trinkets:trinkets@localhost:5432/trinkets`) as durable sandbox inventory and Redis (`redis://localhost:6380`) as a ready-pool index; use k6 and DuckDB. Baseline: every request creates a fresh simulated sandbox with a fixed provisioning delay. Variant: atomically claim an exact-match ready row, then replenish asynchronously. Invariant: each ready sandbox is claimed at most once and every request receives either one unique sandbox or an explicit capacity error. Measure create-to-ready p50/p95, claim conflicts, ready inventory, replenishment lag, and reserved capacity under bursts. This models Daytona's pool bookkeeping; it does **not** measure container startup. [Warm pools](https://www.daytona.io/docs/en/warm-pools/)

2. **Lifecycle reconciliation after a lost runner acknowledgement.** Model API desired state and runner heartbeat timestamps in PostgreSQL, with jobs in configured NATS JetStream (`nats://localhost:4222`). Inject a lost acknowledgement in the mock runner. Keep etcd leases and network-level fault injection as separate follow-ups. Baseline: one fire-and-forget create job. Variant: idempotent job key plus a reconciler that resends when observed state lags desired state. Invariant: a sandbox ID has at most one live allocation despite redelivery; stale runner updates cannot move a terminal deletion back to running. Measure convergence time, duplicate deliveries, transitions, and orphaned allocations in DuckDB. This teaches the state-management problem named in Daytona's architecture, not its unpublished scheduling policy. [Architecture](https://www.daytona.io/docs/en/architecture/)

3. **Snapshot fan-out versus shared mutable volume.** Use configured OCI registry (`localhost:5050`) for an immutable prepared image and SeaweedFS S3 (`http://localhost:8333`, access key `trinkets`, secret key `trinkets-secret`, region `us-east-1`, path-style) for artifacts shared across simulated sandboxes. Baseline: upload each sandbox's input separately. Variant: all sandboxes reference one immutable base and read common objects; write results under distinct prefixes. Invariant: each sandbox sees identical base bytes, and no result overwrites another tenant's key. Measure uploaded bytes, object requests, first-read latency, and per-run storage. This models snapshot/volume economics; S3 objects do not reproduce FUSE consistency or OCI layer mounting. [Snapshots](https://www.daytona.io/docs/snapshots/) · [Volumes](https://www.daytona.io/docs/en/volumes/)

## Future software gap

Real container create/exec/limits measurements need the catalog's **unconfigured** Docker Engine API integration; VM pause/hot snapshot experiments need a VM runtime on an appropriate host. A sandbox daemon, reverse proxy, and FUSE/S3 volume mount are also **unconfigured**. Do not label the control-plane simulations above as isolation or VM benchmarks.
