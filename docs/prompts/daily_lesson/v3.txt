CORE AND EXPERIMENT: KEEP THE FUTURE k6 ADAPTER EASY

The standalone lesson must finish and teach its concept with make lab-<slug>, without an HTTP server or k6. Separate only the reusable operation from its small experiment runner:
  - core/core.go uses package core; core.ts exports functions or a small factory. Export shared DDL as Schema (Go) or schema (Deno) when needed.
  - The core accepts caller-owned clients and explicit inputs/settings, performs the actual storage operation, and returns a small useful result plus errors. Distinguish expected outcomes (duplicate, miss, empty queue, injected failure) from unexpected dependency errors. Define which returned fields are meaningful for each outcome.
  - The runner owns connections, creating/seeding/resetting fixtures, experiment loops, timing, invariant checks, console output, CSV writing, and cleanup. Importing the core must not connect, execute the experiment, or change storage. Core operations must not reset fixtures, print, write CSV, or terminate the process.
  - Keep transactions inside the operation when they express the mechanism. In Go, a small interface matching the required pgx methods can allow either a connection or pool. In Deno, keep each transaction on one checked-out client. Concurrent transactions require separate connections; never share one active transaction across concurrent calls.
  - Use lesson-specific tables, keys, and object prefixes. Reset only this lesson's fixtures. Make key/prefix construction reusable where the adapter will need it. Avoid global mutable experiment state or assumptions that IDs arrive sequentially. Keep concurrency and fixture growth bounded. No service-wide flushes or volume deletion.
Use ordinary functions and minimal types; do not build a framework. Preserve the real mechanism when making it reusable: a later HTTP request should call a single operation or explicitly defined unit of work, not rerun main or reset the whole experiment.
