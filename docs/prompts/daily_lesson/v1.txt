Create a 10-minute systems lesson. Build one small system using one or at most two primary storage systems chosen from PostgreSQL, DuckDB, Redis/Valkey, or SeaweedFS. Use PostgreSQL when the architecture needs a relational database; never use SQLite in this series because the user has a separate SQLite daily lesson. PostgreSQL is not mandatory in every architecture: Redis/Valkey-only systems, SeaweedFS object-storage systems, and appropriate combinations remain in scope. Choose storage to fit the problem rather than forcing a relational database. Pick exactly one main '-ly' property such as reliability, durability, latency, availability, or consistency to teach. Use either Go or TypeScript with Deno. Give a brief problem overview, a text art architecture diagram, the minimum runnable files needed to express the core idea, and commands assuming dependencies are already installed. Measure one meaningful property of the system during the run, export the measurement into a DuckDB-usable file or DuckDB database, and include a few DuckDB queries to inspect the results after the run. Use DuckDB for measurement analysis even when it is not part of the primary architecture. End with what was intentionally skipped for brevity. Favor useful, common systems concepts over clever or rare APIs, and vary the storage engines, architectures, language, and measured property across lessons.
